## Gold tables

Written only by the Databricks Gold build (spec section 17, rule 13). Full definitions in [docs/metrics.md](docs/metrics.md).

| Table | Role |
|---|---|
| `dim_customer`, `dim_product`, `dim_campaign`, `dim_date` | Dimensions. Surrogate keys are `GENERATED BY DEFAULT AS IDENTITY`; key -1 is the unknown member (not `dim_date`) |
| `fact_orders`, `fact_order_lines`, `fact_attribution` | Base facts, one row per order, order line, and order and attribution model |
| `agg_orders_daily` | Orders and revenue by day, channel, payment method, platform |
| `agg_funnel_daily` | Sessions and abandon rates by day, country, channel, platform |
| `agg_campaign_daily` | Campaign spend, orders and ratios per report date (last touch) |
| `agg_city_product_daily` | City, product, day views, carts and sales |
| `rec_product` | Co-view product recommendations |
| `customer_360` (stretch) | Customer current state |

## Address and tracking

An address is country, city, then district (spec section 18). Districts are the official Egyptian subdivisions of each city (for example Nasr City, Maadi and Heliopolis under Cairo; Dokki, Agouza and Imbaba under Giza); a missing or mismatched district is stored as `unknown`. Campaign traffic is tracked by UTM parameters inside the page URL (`page_url`); Silver parses `utm_source`, `utm_medium` and `utm_campaign` from it.

## Yesterday's ad report

Airflow DAG `ads_yesterday_report` (03:00 UTC daily, `airflow/dags/`, logic in `batch/ads_report.py`) pulls the ad API for yesterday once, stores it in `silver_campaign_snapshots` and writes `data/reports/ads_report_<date>.json`. A rerun on the same day returns the stored report without calling the API. Start Airflow with `docker compose --profile airflow up -d airflow`. Details in [docs/RUNNING.md](docs/RUNNING.md).

## Quick start

Windows, PowerShell, from the repo root. Needs Docker Desktop and Python 3.11.

```powershell
Copy-Item .env.example .env                       # then set your own passwords; never commit .env
python -m venv .venv
.venv\Scripts\python -m pip install -r requirements.txt
docker compose build spark
docker compose up -d kafka postgres grafana
.venv\Scripts\python kafka/create_topics.py
docker compose run --rm spark python scripts/seed_silver_reference.py --lake data/lake   # products and customers; Silver needs them to recognise valid product ids
.\scripts\watch_demo.ps1 -Rate 10 -SyncEvery 0     # opens the Kafka, pipeline and generator windows; Grafana at http://localhost:3000
```

`watch_demo.ps1` also starts Kafka, Postgres and Grafana and creates the topics itself, so the `docker compose up` and `create_topics.py` lines are only needed to prepare them earlier. Stop with `.\scripts\stop_demo.ps1`. Script execution may need `Set-ExecutionPolicy -Scope Process -ExecutionPolicy Bypass`.

## Demo

- Live inventory demo: simulated stock for the dark stores, shown to two users: an operations dashboard with a "Demand on out-of-stock products" alert, and a marketing D-1 view with an estimate of the ad spend exposed to stock-outs. The inventory is simulated and reservations are out of scope. The rehearsal has not been run yet, so no timings are measured.
- Start it with `.\scripts\watch_demo.ps1 -Rate 10 -SyncEvery 0 -Inventory`, then open http://localhost:3000 and the dashboards "Operations, live inventory" and "Marketing, D-1". Steps and the day-after commands: [docs/RUNNING.md](docs/RUNNING.md), section "Live inventory demo".
- Failure demo: kill the Spark job, watch Grafana and the alert, restart, check for duplicates. See [docs/RUNNING.md](docs/RUNNING.md), section "Failure demo (G3)".
- Sample data: CSV files of the Gold and Silver tables in [samples/](samples/) (see `samples/README.md`), so the project can be inspected without Databricks. Regenerate with `scripts/export_samples.py`.
- Benchmark: once the benchmark has run, the report is `docs/benchmark.md`. It is produced by `scripts/benchmark.py`.
- Grafana dashboards: http://localhost:3000 (log in as `admin`), dashboard "FunnelStream: live pipeline".

## Troubleshooting

- Java 17 and Spark live inside the Docker image. Do not install Java on the host. The host needs Python 3.11.
- Docker needs about 8 GB of memory.
- The host does not read `.env`. Scripts that need the Databricks or Postgres settings run in the `spark` container, for example `docker compose run --rm spark python scripts/check_databricks.py`.
- If `localhost:9092` or `localhost:3000` stop answering after Docker Desktop restarts, run `docker compose restart kafka` or `docker compose up -d --force-recreate grafana`.

## Getting started

```bash
cp .env.example .env            # set your own passwords
python -m venv .venv
.venv/Scripts/activate          # Windows
pip install -r requirements.txt
pytest
```

Spark tasks (7 onward) run in Docker. The host needs Python 3.11 only for the simulator and the host tests. Java is NOT needed on the host: Java is inside the Spark Docker image. See [docs/RUNNING.md](docs/RUNNING.md).

## Spark in Docker

Spark needs Hadoop's winutils on Windows, so Spark runs in a container. Spark tests are skipped on the Windows host unless `RUN_SPARK_TESTS=1`.

```bash
docker compose build spark
docker compose run --rm -e RUN_SPARK_TESTS=1 spark python -m pytest tests/test_bronze.py -q
docker compose run --rm spark python -m streaming.jobs.bronze_ingest   # needs Kafka up
```

- Do not commit `.env`, `.venv/`, or data under `data/`.
