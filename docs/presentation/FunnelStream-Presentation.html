[1:15] FunnelStream's answer is one stream of events and two lanes. Everything the store does becomes an event in Kafka. We keep every raw message, then clean it once into a trusted copy called Silver. From Silver, a live lane writes small tables to Postgres within a minute and Grafana shows them with eight alert rules: that is for operations. The simulator. acks=all and idempotent, so a retry never writes twice.

Keeps messages while the job is down. Replays after a crash.

Consumer: the Spark job

Reads each topic in micro-batches. Its checkpoints hold the committed offsets, so a restart resumes where it stopped.

Keys keep order. All events of a session, or of an order, go to one partition in sequence.

Producers and the lake never talk to each other. Either side can fail or be replaced.

Replay is safe. Silver writes are idempotent, so reading a message twice changes nothing.

[1:15] Kafka sits between the producers and everything else. Four topics: app.events with six partitions keyed by session, orders and delivery.events keyed by order id, and inventory.events keyed by store. The key matters: all events of one order land in one partition and stay in order. Our producer uses acks equals all and idempotence, so a retry does not write twice. The consumer is a Spark job that reads in micro-batches and stores the committed offsets in checkpoints. That is the point of the messaging layer: if the Spark job is killed, Kafka keeps the messages, and the restarted job resumes from its checkpoint. In the HTML version the dots show the data flowing.

Rejected rows go to quarantine with one of these reasons

BAD_JSON

MISSING_FIELD

NEGATIVE_PRICE

FUTURE_TIMESTAMP

UNKNOWN_PRODUCT

Evidence, 13 October 2026: quarantine count matched the noise manifest (308 expected, 308 observed). Replaying Bronze left all 10 Silver tables unchanged.

[1:30] Follow one message: a new order. It arrives on the orders topic with the order id as key. Bronze stores the raw value plus the Kafka partition, offset and ingest time, and never changes it. Then the validator checks it against a versioned schema. If the JSON is broken, a field is missing, the price is negative, the timestamp is in the future or the product is unknown, the row goes to quarantine with an error code and never reaches the numbers. If it passes, Silver types it, converts the time to UTC, deduplicates on the event id and writes it with a Delta MERGE on the key, so a replay inserts nothing. Order status is decided by rank, not by arrival order. Two checks prove it: the quarantine count equals the noise the simulator injected, 308 for 308, and replaying Bronze left all ten Silver tables unchanged.

[1:15] Data lives in three layers. Bronze keeps every raw message and is never changed. Silver is trusted: one row per key, typed, deduplicated, with a quarantine table for rejected rows. Both run as Delta folders on the laptop, and Silver can be rebuilt from Bronze at any time. Gold is business ready and lives in Databricks: facts for orders, order lines and attribution, slowly changing dimensions for customers and products, daily aggregates for orders, funnel, campaigns and city by product, and a customer 360 table. Twelve Gold tables are built; a thirteenth slot for recommendations is empty on purpose. Operational data for Grafana lives in Postgres: sixteen small live and serving tables, plus the daily marts that Power BI also reads.

[1:15] Reliability is built in layers. If the Spark job is killed, checkpoints hold the Kafka offsets and the restart resumes from them. How the next morning's number is computed

oos_click_share

= out-of-stock landing clicks / served landing clicks

exposed_spend

= spend x oos_click_share

revenue_at_risk

= add-to-carts on out-of-stock products x price
